## 1. triage：怎么判断题目难易

**参考实现**：
- Cairn：**没有 triage**。题目由人给 origin/goal，价值判断全靠 reason 的 LLM 语义规则
  （reason.md:30-39 "propose high-value and non-overlapping directions"，不是可计算分数）。
- verialabs：也没有。新题一律 spawn swarm 全模型竞速（无限预算哲学）。
- Koshary：**最接近**——`strategy_rank = points + 40*has_files + 25*kind_bonus - 30*failed_attempts`
  （orchestrator.py:1046-1057），纯规则打分决定求解顺序。
- LLM-CTF-Solver：有 `challenge_classifier` 做 LLM 题型分类（非难度）。

**我们的决策**：Koshary 公式打底 + LLM 难度评估 + 动态修正：
1. `rank = points*1.0 + 40*has_files + 25*kind_bonus - 30*failed_races`（移植 Koshary 公式，把 failed_attempts 换成 races）；
2. 加一层 LLM triage：描述 → `{difficulty 1-5, 理由}`，只在 points 缺失/同分时用；
3. 动态降级：races 失败后 rank 扣分而不是直接 dead（Koshary 的 `-30*failed_attempts` 语义就是"失败降权不放弃"——我们现在的"races 预算耗尽→dead"比参考实现更激进，3h 赛里应该改成"降权等待人工提示"）。

## 2. planning：模型与质量

**参考实现**：
- Koshary：**plan 复用求解同一个模型 CLI**（orchestrator.py:821 → generate_challenge_plan 的 runner_cmd），
  "You are a CTF Planning Agent" prompt → markdown 计划写 plan.md → `{plan}` 注入每轮 prompt；
  **无质量校验**，失败降级 "No plan generated."（orchestrator.py:677-708）。
- Cairn：无 planner，reason 任务承担"下一步方向"决策（分层监督，见 §5）。
- 我们现状：planning.py 用 `deepseek-chat`（便宜模型）——**这是我们对参考实现的偏离，不是继承**。

**我们的决策**（用户要求强模型，正确）：
1. `planner_routing`：easy→flash，medium/hard→v4-pro（或后续 GPT/Claude），配置进 l2-config.json；
2. 质量门禁：步骤 <3 或空话率过高 → 重生成一次（Koshary 没有，我们补）；
3. **失败重规划**（我们独有场景）：worker 僵局击杀时把失败摘要喂给 planner 重新出计划——参考实现都没有
   （它们要么无限重试要么靠人），3h 限时下这是我们止损的关键设计；
4. A/B 验证：`--no-planning` 开关 + benchmark 对照。

## 3. 模型路由与多模型接入

**参考实现**：
- Koshary：静态路由表（config.json:68-89：web/forensics/mobile→gemini、crypto/reverse/misc→claude、
  pwn→codex），`choose_route` 子串匹配（orchestrator.py:214-219）→ 细化 model_key → runner+prompt 模板。

**我们的决策**：Koshary 路由（静态、零成本、可预期）为主 + verialabs 竞速（限 2 路）为辅 +

OpenAI=`api:"openai-completions"`+`$OPENAI_API_KEY`，Claude=`api:"anthropic-messages"`+`$ANTHROPIC_API_KEY`，
key 用 `$ENV` 占位符。等用户给 key 即接入。

**参考实现**：

  `<workspace_root>/<project_id>/` 目录，子进程执行（我们 Kali REST 的形态等价物）。

## 5. 监督模块（benchweava 思路的源码实证）

**参考实现**：
- **Cairn reason 任务 = 最完整的分层监督**（research-cairn §3）：只读图 YAML 快照 + open intents，
  输出 `complete/intents/noop` 三种动作；靠 `create_intent` 给 explore 供料、`complete` 收束项目；
  触发去重靠 ReasonCheckpoint 记录 fact/hint/intent 三个计数（loop.py:704-718）。
- **verialabs coordinator = 最轻量的监督**（coordinator_core.py:133-171）：读每 solver JSONL 尾部
  last_n 行折叠成可读摘要 → bump 注入具体指引；人消息走 operator_inbox 由 coordinator LLM 转译。

**我们的决策**：合成两者的轻量版 supervisor.py：
1. 每 5 分钟读 worker 事件流尾部 → 强模型输出 `{verdict: on_track|off_track|stuck, correction}`；
2. `off_track` → 注入纠偏；`stuck` → 杀 + 失败摘要重规划（与 §2 联动）；
3. 注入通道：pi 扩展 `pi.sendUserMessage({deliverAs:"steer"})`（research-pi §6 已证实可行）；
4. 成本控制：只对 medium/hard 开监督；easy 靠 flash 裸跑。
（benchweava 源码等用户提供后按同法拆解，再修订本节。）

## 6. 提交纪律（冷却/去重/上限）

**参考实现**：
- verialabs（swarm.py:152-192，逐行已核验）：`[0,30,120,300,600]`s，**按模型计数**（_submit_count
  的 key 是 model_spec）、跨模型精确去重、asyncio.Lock 串行；**无硬上限**，冷却封顶 600s 永不禁赛；
  `already_solved` 也算确认（防同队重复提交）。
- Koshary：**完全没有冷却/限流/重试**，只有 attempted_flag 去重 + max_wrong 硬上限
  （HTB 默认 3、CTFd 默认 0=不限；**异常提交也计数**，orchestrator.py:968-978）。
- Cairn：零纪律，只有 skill 提示词软约束"高置信才提交"。

**我们的决策**：
1. 冷却表参数化（l2-config）+ **改成按模型计数**（修正现状的按题计数——verialabs 的证据表明
   一个坏模型不该拖累另一个模型的提交节奏）；
2. 保留 max_wrong=3 硬上限但改为"看板一键解锁"（比 verialabs 严、比 Koshary 松——DASCTF 未探明前保底防封号）；
3. 8/18 测试赛用 probe 脚本实测平台限流真实参数，回来只改配置数字。
（教训：三个参考实现的提交纪律天差地别，说明平台规则决定一切——没有实测就没有正确答案。）

## 11. 隔离：容器 vs 软隔离

**参考实现**：
- Cairn：**每项目一个容器**（cairn-dispatch-<project_id>，sleep infinity 常驻，containers.py:31-72）；
  文件 put_archive tar 注入无 bind mount；限资源只有 timeout -k + cap_add + network_mode，
  **连 Cairn 都没有内存/CPU 硬配额**（research-cairn §7 明确）；另有 local_backend 无容器版。
- verialabs：**每模型一个容器** + 每容器唯一 mkdtemp 目录绑 /challenge/workspace（rw）、
  distfiles ro、16GB 内存 + 2 CPU（sandbox.py:109-149）；exec 包 timeout --signal=KILL。
- LLM-CTF-Solver：SSH + 本地 AST 沙箱（python 工具）。

**我们的决策**（用户 VPN 可解 registry）：
1. **8/18 前（必须）**：软隔离 = `/root/ctf/<cid>/w<idx>/` 每 worker 独立目录（≈Cairn local_backend 模式）
   + 现有进程组杀 + 命令 timeout——这是"无容器官方实现"给的底气，够解静态题；
2. **VPN 通后**：容器优先用于**服务类题靶机**（cybench/CTFTiny 自带 docker-compose，这是容器不可替代处）；
3. **worker 全容器化**排在服务题之后（API 改造 + 镜像构建回归风险 > 收益，8/21 前不动）。
