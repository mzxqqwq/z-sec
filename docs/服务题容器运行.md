# 服务题容器运行（benchmark 靶机重建）

> 状态：已实现并端到端验证（2026-08-17）。
> 解决的问题：CTFTiny/NYU 服务题的 box 是 CSAW 当年的公网靶机，早已下线，
> 服务题能力无法评测。做法很简单：**把题目官方的 docker 镜像拉到 Kali，
> 起一个容器当靶机**，worker 连 127.0.0.1 解题。
> 代码里的标识符沿用 `revive`（--revive / CTF_REVIVE / revival.py），文档统一叫「容器运行」。

## 原理

llmctf/* 镜像发布在 docker.io（flag 当年构建时烘焙进镜像内部，本来就是攻击面）。
镜像已在 Kali 本地时：

1. `podman run` 起容器，容器端口映射到 **Kali 127.0.0.1 的空闲高端口**（21000 起）；
2. 平台把挑战的 `box` 覆盖为 `127.0.0.1`、`port` 覆盖为该高端口；
3. 探测确认服务可答后，worker 在 Kali 内直连解题（解题动作与真实比赛一致）。

多服务题（如 web+db）：同一 podman 网络内按 compose 顺序启动，
仅前置服务（端口含 internal_port 的那个）做宿主机端口映射。

## 完整性

- 起容器**不复制任何题库文件到 Kali**；flag 只存在于容器内部（服务题攻击面）；
- worker 禁 podman/docker 命令（提示词已有禁令，transcript 可审计）。
- 探测只在 `--revive` 开启时做（dead → 尝试起容器）；不开时不探测，
  成绩单不区分靶机状态（旧的探测徽标/成绩单排除功能 2026-08-17 已下线）。

## 使用

### 0. 一次性：拉取镜像（Kali 上，VPN 开着）

```bash
# CTFTiny 50 题需要 27 个镜像（约 10-13GB），已全部就位
sudo bash /root/pull-ctftiny.sh
# 磁盘充足（≥100GB 余量）时再全量（165 个镜像约 65-90GB）：
sudo bash /root/pull-service-images.sh   # 失败可加参数重试次数：bash pull-service-images.sh 3
```

- 全量 165 个唯一镜像（162 llmctf/* + mongo/nginx/postgres），
  清单由 `extract-service-images.py` 从 183 个 compose 文件精确提取；
- 拉过后镜像留在 podman 本地存储，**之后跑 benchmark 不需要 VPN**；
- docker-in-docker 类题（如 describe-me）建议顺手启用 podman 套接字：

```bash
sudo systemctl enable --now podman.socket   # 提供 /run/podman/podman.sock
```

### 1. 跑分时开启容器运行

```powershell
# 方式 A：看板 Benchmark 页跑分——先在跑看板的 PowerShell 里设置环境变量
$env:CTF_REVIVE = "1"
#（bench_admin 读到该变量就给 eval_run 加 --revive；改完重启看板生效）

# 方式 B：命令行直跑
python D:\ctf-agent\src\ctf_orchestrator\eval_run.py --platform ctftiny --revive `
    --workspace D:/ctf-agent/eval-workspace-bench --max-rounds 3
```

- 只在「探测为 dead」时尝试起容器，且仅对镜像已存在的题生效（缺镜像的跳过，
  日志输出 `image_missing:...`，跑分不受影响）；
- 跑分结束自动 `podman rm -f` + 删网络，不留残留容器。

## 特殊服务题（HOST_OVERRIDES）

docker-in-docker/多阶段交互题无法用通用 `podman run -d -p` 起服务。首个落地案例
**msc-showdown**（CSAW 2018 Finals，镜像从未发布到 docker hub）：

- flag 烘焙进内层镜像 `llmctf/2018f-msc-showdown-container`（本地构建，构建脚本
  `src/tools/make_showdown_build.py` + `build_showdown.py`），不落 Kali 磁盘；
- 宿主跑 `socat TCP-LISTEN:9222 EXEC:podman run 会话容器`，每连接一个 --rm 容器，
  语义与原版外层 dond 一致（banner → sudo su cowhand → 退出打印 ASCII-art flag）；
- 机制：`revival.py` 的 `HOST_OVERRIDES` 表（cid → port/start/stop），revive() 先查
  这张表再走通用流程；stop 按 stop 命令清理。已验证全链路（whoami=cowhand、退出出
  art flag、清理正常）。
- 踩坑记录：仓库检出 CRLF 会毁掉 shebang（`-i\r` → bash 非法选项）与 sudoers/flag，
  构建上下文必须统一转 LF。

## 已知限制

- **46 道中央 runner 托管题**（目录无 Dockerfile/compose，如 rev/rap、rev/checker、
  cry-perfect-secrecy 等，当年跑在 CSAW 统一 checker 服务上）无法起容器；
  清单见 `src/tools/_check_blind.py`。
- 宿主路径卷（编排机特有目录）不存在时跳过该卷——题仍能起，行为降级。
- 端口分配 21000-21500，同 run 内顺序分配无冲突。

- `src/tools/_smoke_revive.py` / `_smoke_platform.py` —— 冒烟回归脚本
