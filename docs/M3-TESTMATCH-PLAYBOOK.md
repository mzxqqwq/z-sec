# M3 测试赛行动手册（8/18 09:00–8/19 17:00）

> 目标：在低风险窗口内拿到真实平台 API 全貌并跑通"拉题→解题→交卷→查分"闭环。
> 人员：1 人（用户）+ 开发代理（DSH）。

## 时间线（8/18 09:00 开赛后立即执行）

### 第 0-10 分钟：登录与凭证
1. 用浏览器（人）登录平台，确认 AI 赛道入口可见
2. 设置环境变量：`DASCTF_BASE_URL` / `DASCTF_USERNAME` / `DASCTF_PASSWORD`（或提供 cookie）
3. 跑 `python probe_platform.py --base-url <真实地址>`（探测脚本已就绪）

### 第 10-40 分钟：API 摸底
1. 阅读 probe 报告：确认登录端点、题目列表形状、附件下载、提交接口
2. 如有 captcha/加密：从 probe 的 config 端点确认类型（HashPow/Turnstile/图形码）
3. 用 curl/requests 手工验证 1-2 个端点，确认响应结构
4. 把真实端点填入 dasctf_client 的 EP 类（全部改动集中在这一处）

### 第 40-90 分钟：最小闭环验证
1. 手动解一道最简单题（或让 worker 打一道），验证：拉题→附件→Kali→解题→提 flag→交卷→查分
2. 记录平台行为：提交冷却、错交惩罚、flag 格式、动态计分、题量题型分布
3. 若平台是 CTFd 类：对照 verialabs/Koshary 的 CTFd 适配经验（token/nonce/轮询）

### 第 90 分钟起：全自动小规模试打
1. 启动编排器 `--loop 60`，观察 30 分钟
2. 人盯盘：只写 hints、调优先级，不手工解题
3. 记录问题清单（进入 M4 修复）

### 8/18 晚间复盘
- 问题清单 → 优先级 → 8/19 白天修
- 8/19 下午再试打一轮验证修复

## 已知风险与预案
| 风险 | 预案 |
|---|---|
| 平台 API 带 HashPow/加密 | dasctf_client 预留了钩子；按标准算法实现（X25519+AESGCM / SHA256 PoW） |
| 提交冷却比预期长 | 递增冷却 [0,15,60,180] 已在 v2.1 设计里；先观测平台真实值再调 |
| 附件是大文件/多文件 | kali_upload 已是 base64 通道；确认附件下载端点支持范围请求 |
| 平台限频（429） | 客户端已有指数退避；记录 Retry-After 真实值 |
| API 结构与猜想完全不同 | probe 报告 + SPA bundle 分析是第一手证据；EP 集中改，1 小时内可适配 |
| 题目带动态靶机（nc/HTTP 端口） | 题目描述里的连接信息会注入 worker 提示词；worker 经 Kali 连靶机 |

## 测试赛验收标准（M3 done 判据）
- [ ] 真实平台登录成功（cookie 持久化）
- [ ] 拉题/附件/交卷/查分四端点全部打通
- [ ] 至少 1 道题由编排器全自动解出并成功交卷
- [ ] 平台行为清单（冷却/限频/flag 格式/计分）记录在案
- [ ] 问题清单进入 M4
